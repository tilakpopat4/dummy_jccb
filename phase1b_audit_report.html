1. Root Cause Analysis: How Branch Terminals Overwrite Master Settings

There are three concurrent mechanisms in the codebase enabling branch operators to mutate or overwrite bank-wide configuration documents:

A. Automated 5-Second Background Sync Fallbacks (syncCloudData)

In app_gold.js (lines 946-964), the automated sync timer executes every 5,000ms on all 120+ branch machines. If a fetch for bank rules or settings momentarily returns empty or times out, the branch machine immediately pushes its local localStorage state back to the cloud:

// app_gold.js (Lines 947-964) if (typeof window.FirebaseService.getRules === "function") { const fbRules = await window.FirebaseService.getRules(); if (fbRules && typeof fbRules === "object" && fbRules.membership) { state.rules = { ...state.rules, ...fbRules }; } else if (state.rules && state.rules.membership) { // ⚠️ ANY branch terminal pushes its local rules to Firestore if fetch is empty! window.FirebaseService.saveRules(state.rules).catch(() => { }); } }

B. Continuous Unconditional Valuer Master Writes

In app_gold.js (line 1031), window.FirebaseService.saveValuersList(state.valuers, state.deletedValuerIds) is called unconditionally on every single 5-second sync cycle from every single connected terminal, causing continuous concurrent write race conditions across 120+ machines.

C. Missing Role Checks on Master Setting Forms & Zero Server-Side Rules

  • UI Handlers: In app_gold.js (lines 7200-7214), the Rules Master save form does not verify if state.currentSession.code === "99". Any branch operator can edit deduction percentages or LTV rules and commit them directly.
  • Firestore Rules: firestore.rules contains allow read, write: if true;, providing zero database-level authorization.

3. Security Architecture Blueprint for PostgreSQL & Supabase

The table below outlines how every write vulnerability identified above will be permanently resolved at the database engine level in PostgreSQL using Row-Level Security (RLS) and constraints:
Resource / Table Current Vulnerability in Firestore PostgreSQL & Supabase Security Architecture
Master Rules & Settings
(rules_master, bank_settings, products, valuers)		 Branch terminals overwrite bank-wide settings via 5s sync loop and unvalidated forms. Postgres RLS Policy:
FOR SELECT TO authenticated USING (true);
FOR ALL TO authenticated USING (auth.jwt() ->> 'role' = 'admin' AND auth.jwt() ->> 'branch_id' = '99');
Branch users receive a hard SQL 403 Forbidden on any write attempt.
Loan Applications
(loans, loan_ornaments)		 Any branch can modify or delete loans belonging to other branches. Branch-Scoped RLS:
FOR ALL TO authenticated USING (auth.jwt() ->> 'role' = 'admin' OR branch_id = (auth.jwt() ->> 'branch_id')::text);
Branch users can only insert, update, or delete loans within their assigned branch.
Security Audit Trail
(audit_logs)		 Audit logs can be modified or deleted by clients. Immutable Append-Only Table:
FOR INSERT TO authenticated WITH CHECK (true);
FOR UPDATE, DELETE TO authenticated USING (false);
No user, including admins, can modify or delete historical audit entries.
Daily Gold Rates
(rates)		 Unprotected daily rate updates. Locked Rates Enforcement:
Only HO Super Admin can insert/update rates. If is_locked = true, a database trigger rejects further updates for that date.
